▶ 인덱스 추가 (즉시 적용, 비용 0원)
--------------------------------------------------------------------------------
-- QR코드 조회 최적화
CREATE INDEX idx_qrcodes_code ON qr_codes(code);

-- 팔로우 관계 조회 최적화
CREATE INDEX idx_user_follows_admin_active ON user_follows(admin_id, is_active);
CREATE INDEX idx_user_follows_user_admin ON user_follows(user_id, admin_id, is_active);

-- 방명록 조회 최적화
CREATE INDEX idx_guestbook_qrcode ON guestbook_messages(qr_code_id);
CREATE INDEX idx_guestbook_qrcode_created ON guestbook_messages(qr_code_id, created_at DESC);

-- 랜딩페이지 설정 조회 최적화
CREATE INDEX idx_landing_qrcode ON landing_page_settings(qr_code_id);


▶ Read Replica 분리 (월 10~20만원)
--------------------------------------------------------------------------------
  [애플리케이션]
       │
       ├── 쓰기 (INSERT/UPDATE/DELETE) ──→ [Primary DB]
       │                                        │
       └── 읽기 (SELECT) ──→ [Read Replica 1] ←─┤
                         └──→ [Read Replica 2] ←─┘

  - Primary: 쓰기 전용
  - Replica: 읽기 전용 (2~3대)
  - 읽기:쓰기 비율이 9:1 이상일 때 효과적


▶ 쿼리 최적화
--------------------------------------------------------------------------------
  AS-IS (5번 DB 왕복):
    1. QRCode 조회
    2. 팔로워 수 COUNT
    3. 방명록 수 COUNT
    4. 팔로우 여부 확인
    5. 랜딩페이지 설정 조회

  TO-BE (1번 DB 왕복):
    - 서브쿼리로 통합하여 단일 쿼리 실행
    - 현재 구현됨 ✓


================================================================================
                           2단계: 캐싱 레이어 (Redis)
================================================================================

▶ Redis 도입 (월 5~10만원)
--------------------------------------------------------------------------------
  [클라이언트] → [API 서버] → [Redis] → [PostgreSQL]
                                ↑
                           캐시 히트 시
                           DB 조회 생략


▶ 캐시 대상 및 TTL 설정
--------------------------------------------------------------------------------
  데이터 종류          │ TTL    │ 이유
  ─────────────────────┼────────┼─────────────────────────
  매장 프로필          │ 5분    │ 거의 변경 안됨
  매장 로고/설정       │ 10분   │ 변경 빈도 낮음
  팔로워 수            │ 1분    │ 실시간성 필요
  방명록 수            │ 1분    │ 실시간성 필요
  피드 목록            │ 30초   │ 새 글 반영 필요
  사용자 팔로우 여부   │ 30초   │ 토글 반영 필요


▶ 캐시 구현 예시 (C#)
--------------------------------------------------------------------------------
  public async Task<StoreProfileResponse> GetStoreProfile(string qrCode)
  {
      var cacheKey = $"store:profile:{qrCode}";

      // 1. 캐시 확인
      var cached = await _redis.GetAsync<StoreProfileResponse>(cacheKey);
      if (cached != null)
          return cached;

      // 2. DB 조회
      var result = await _context.QRCodes
          .Where(q => q.Code == qrCode)
          .Select(...)
          .FirstOrDefaultAsync();

      // 3. 캐시 저장
      await _redis.SetAsync(cacheKey, result, TimeSpan.FromMinutes(5));

      return result;
  }


▶ 캐시 무효화 전략
--------------------------------------------------------------------------------
  - Write-Through: 데이터 변경 시 캐시도 함께 업데이트
  - Cache Invalidation: 데이터 변경 시 캐시 삭제 → 다음 조회 시 갱신

  예시:
    팔로우 시 → $"store:{adminId}:followers" 캐시 삭제
    방명록 작성 시 → $"store:{qrCode}:guestbook:count" 캐시 삭제

================================================================================
                          4단계: CDN + Edge 캐싱
================================================================================

▶ 전체 아키텍처
--------------------------------------------------------------------------------
  [사용자]
      │
      ▼
  [CDN] ─────→ 정적 리소스 (JS, CSS, 이미지)
      │
      ▼
  [API Gateway] ─→ Rate Limiting, 인증
      │
      ▼
  [Load Balancer]
      │
      ▼
  [API Servers] ←→ [Redis] ←→ [PostgreSQL]


▶ CDN 캐싱 대상
--------------------------------------------------------------------------------
  리소스 종류          │ TTL      │ 캐시 위치
  ─────────────────────┼──────────┼─────────────
  JS/CSS 번들          │ 1년      │ CDN Edge
  이미지 (로고 등)     │ 1주      │ CDN Edge
  폰트                 │ 1년      │ CDN Edge
  API 응답             │ 안함     │ Redis


▶ CloudFlare 설정 예시
--------------------------------------------------------------------------------
  Page Rules:
    - *.js, *.css → Cache Level: Cache Everything, TTL: 1 year
    - /uploads/* → Cache Level: Cache Everything, TTL: 1 week
    - /api/* → Cache Level: Bypass

                        5단계: 이벤트 기반 비동기 처리
================================================================================

▶ 메시지 큐 도입 (RabbitMQ / AWS SQS)
--------------------------------------------------------------------------------
  동기 처리 (AS-IS):
    팔로우 버튼 클릭 → DB 저장 → 카운트 업데이트 → 알림 발송 → 응답

  비동기 처리 (TO-BE):
    팔로우 버튼 클릭 → DB 저장 → 응답 (즉시)
                            ↓
                      [Message Queue]
                            ↓
              ┌─────────────┴─────────────┐
              ▼                           ▼
        [카운트 업데이트]           [알림 발송]


▶ 비동기 처리 대상
--------------------------------------------------------------------------------
  - 팔로워 수 업데이트
  - 좋아요 수 업데이트
  - 푸시 알림 발송
  - 이메일 발송
  - 통계 집계
  - 로그 저장
